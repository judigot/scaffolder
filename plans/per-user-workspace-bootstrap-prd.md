# PRD: Per-User Dedicated Workspace EC2 Bootstrap

## Document Metadata

- **Status**: Done
- **Owner**: Scaffolder Platform
- **Last Updated**: 2026-02-06
- **Related Repos**:
  - `judigot/scaffolder`

---

## 1) Executive Summary

We should move to a **per-user dedicated EC2 workspace model** where each user gets their own instance, own domain/subdomain, own OpenCode credentials, and own cloned `judigot/workspace` repository.

This is a sane and strongly recommended architecture for security and operational clarity. It eliminates cross-user file access risk present in shared-host designs and aligns with how OpenCode currently works best (single working context per instance).

This PRD defines a complete product and implementation plan for:

1. Provisioning a user-specific EC2 instance from Scaffolder.
2. Bootstrapping `judigot/workspace` on first start.
3. Injecting per-user workspace configuration (domain, credentials, optional API key).
4. Running `workspace/scripts/init.sh` in unattended/safe mode.
5. Returning a ready-to-use workspace URL to the user.

---

## 2) Problem Statement

### Current Risk

In a shared-instance setup, authenticated users can potentially access other users' repositories or runtime context if process-level and filesystem-level isolation are not strict enough.

### Why This Matters

- OpenCode is powerful and filesystem-aware.
- Any accidental shared context can become data leakage.
- Multi-tenant hardening on a single box is possible but complex and fragile.

### Desired Outcome

Each user should have:

- Dedicated compute boundary (EC2 instance).
- Dedicated filesystem and processes.
- Dedicated workspace configuration and credentials.

---

## 3) Goals

1. **Isolation by default**: one user = one EC2 instance.
2. **One-click bootstrap** from Scaffolder using `judigot/workspace`.
3. **Domain-aware setup** per instance.
4. **Secure-by-default OpenCode auth** with non-shared credentials.
5. **Consistent developer UX**: user lands on working `https://<workspace-domain>`.
6. **Operational repeatability**: idempotent bootstrap/rebuild.

---

## 4) Non-Goals (for this phase)

1. Multi-user shared instance isolation.
2. Per-app isolated OpenCode instances on the same host.
3. Full tenant billing automation design (can be layered later).
4. Kubernetes migration.

---

## 5) Recommended Product Decision

## Decision

**Yes**: each user should get their own EC2 instance, and that instance should install/initialize `judigot/workspace` as bootstrap.

### On the requested fields

- **Domain field**: **Required**. This should be explicit in Scaffolder workspace provisioning.
- **Default OpenCode credentials**: use with caution.
  - Recommended interpretation: provide a **defaulting mechanism**, not a static shared secret.
  - Scaffolder should auto-generate per-instance credentials when none supplied.
  - Never reuse global default credentials across users.

## 7) Primary User Journey

1. User selects "Create Workspace" in Scaffolder.
2. User enters:
   - `workspaceName`
   - `domain` (or subdomain strategy)
   - optional provider/region/instance type
3. Scaffolder provisions EC2 + DNS + security group.
4. Scaffolder bootstraps machine:
   - clone `judigot/workspace` into `~/workspace`
   - generate `.env` with per-user values
   - run `scripts/init.sh`
5. Scaffolder performs health checks.
6. User gets "Ready" with URLs:
   - `https://<domain>`
   - `https://opencode.<domain>`
7. User uses workspace independently; no cross-user sharing.

## 8) Functional Requirements

### 8.1 Provisioning Input Model (Scaffolder)

Add/confirm these fields in workspace provisioning form/config:

```ts
interface WorkspaceProvisionRequest {
  workspaceName: string;
  ownerUserId: string;

  // Required for bootstrap
  domain: string; // e.g. dev-alice.judigot.com OR alice-workspace.example.com

  // Optional override; autogenerated if absent
  opencodeUsername?: string;
  opencodePassword?: string;

  // Optional credentials
  anthropicApiKey?: string;

  // Infra options
  region?: string;
  instanceType?: string;
  sshPublicKeyName?: string;
}
```

### 8.2 Bootstrap Behavior

For each new instance:

1. Install base dependencies (node, pnpm, nginx, certbot, git, etc.).
2. Clone `judigot/workspace` to `/home/ubuntu/workspace`.
3. Create `/home/ubuntu/workspace/.env` using template + overrides.
4. Ensure `OPENCODE_SERVER_USERNAME/PASSWORD` are set (generated if not provided).
5. Run `~/workspace/scripts/init.sh` non-interactively where possible.
6. Run `~/workspace/scripts/deploy-nginx.sh` as finalization.
7. Validate URLs return expected status codes.

### 8.3 Generated Workspace Config Requirements

`.env` must include at minimum:

```env
DOMAIN=<user-domain>
OPENCODE_PORT=4097
OPENCODE_SERVER_USERNAME=<generated-or-provided>
OPENCODE_SERVER_PASSWORD=<generated-or-provided>
DASHBOARD_PORT=3200
DASHBOARD_API_PORT=3100
APPS=""
DEFAULT_APP=
```

Optional when provided:

```env
ANTHROPIC_API_KEY=<optional>
```

### 8.4 Credential Policy

1. Never hardcode shared default passwords in code.
2. If user does not provide creds:
   - generate random username/password per instance.
3. Store generated credentials encrypted in Scaffolder metadata/secrets storage.
4. Expose once to user at completion screen (with copy action).

### 8.5 Domain/TLS Policy

1. Domain is mandatory for production-ready provisioning.
2. Certbot issuance must run as part of bootstrap (`init.sh` already supports this model).
3. Workspace status remains `provisioning` until cert and nginx health checks pass.

---

## 9) Security Requirements

### 9.1 Isolation

- One tenant/user per EC2 instance.
- No shared filesystem between users.
- No shared OpenCode process between users.

### 9.2 Access Control

- `opencode.<domain>` must enforce basic auth via nginx (`auth_basic`).
- Credentials unique per instance.
- Rotate credentials from Scaffolder UI/CLI in future phase.

### 9.3 Secret Handling

- Avoid logging raw secrets in provisioning logs.
- Mask secrets in UI and logs.
- Pass secrets via secure channel (SSM/user-data secret injection pattern).

### 9.4 Network Defaults

- Restrict inbound ports to 80/443/22 (or 22 optional via SSM).
- OpenCode backend remains bound to localhost and reverse-proxied by nginx.

## 10) Proposed Technical Architecture

### 10.1 High-Level Components

1. **Scaffolder Workspace Provisioner** (new/extended module)
2. **Infrastructure Adapter** (Terraform/API wrapper)
3. **Bootstrap Runner** (cloud-init/SSH command runner)
4. **Workspace Health Monitor**
5. **Workspace Metadata Store** (domain, instanceId, status, creds ref)

### 10.2 Bootstrap Sequence (Detailed)

```text
Scaffolder API
  -> create workspace record (status=queued)
  -> provision EC2 + DNS (status=infra_ready)
  -> wait for SSH/SSM reachable
  -> bootstrap commands:
       - git clone judigot/workspace ~/workspace
       - write ~/workspace/.env
       - cd ~/workspace && ./scripts/init.sh
       - ~/workspace/scripts/deploy-nginx.sh
  -> health checks:
       - https://<domain> == 200
       - https://opencode.<domain> == 401 unauthenticated
       - authenticated opencode == 200
  -> status=ready
```

### 10.3 Data Model Additions (Scaffolder)

```ts
interface WorkspaceInstance {
  id: string;
  ownerUserId: string;
  workspaceName: string;

  // Infra
  cloudProvider: 'aws';
  region: string;
  instanceId: string;
  publicIp?: string;

  // Access
  domain: string;
  opencodeDomain: string;

  // State
  status:
    | 'queued'
    | 'infra_provisioning'
    | 'infra_ready'
    | 'bootstrap_running'
    | 'health_checking'
    | 'ready'
    | 'failed';
  statusReason?: string;

  // Secrets refs (not plain values)
  opencodeUsernameSecretRef: string;
  opencodePasswordSecretRef: string;
  anthropicApiKeySecretRef?: string;

  createdAt: string;
  updatedAt: string;
}
```

## 11) API Requirements (Scaffolder)

### 11.1 Create Workspace

`POST /api/workspaces`

Request body uses `WorkspaceProvisionRequest` above.

Response:

```json
{
  "id": "ws_123",
  "status": "queued"
}
```

### 11.2 Get Workspace Status

`GET /api/workspaces/:id`

Returns status, domains, progress stage, and last known health checks.

### 11.3 Retry Bootstrap

`POST /api/workspaces/:id/retry-bootstrap`

Re-runs bootstrap from `infra_ready` stage.

### 11.4 Rotate OpenCode Credentials (Phase 2)

`POST /api/workspaces/:id/rotate-opencode-creds`

Actions:

1. Generate new credentials.
2. Update `.env` on instance.
3. Run `deploy-nginx.sh`.
4. Return one-time credential reveal.

## 13) Operational Requirements

### 13.1 Idempotency

Re-running bootstrap should be safe:

- `init.sh` already designed to be idempotent.
- `deploy-nginx.sh` can run repeatedly.
- Clone step should handle existing directory gracefully.

### 13.2 Observability

Capture:

- Provisioning lifecycle logs
- Bootstrap command stdout/stderr (sanitized)
- Health check results

### 13.3 Failure Handling

Common failures:

- DNS not propagated yet
- certbot challenge failure
- package install failure
- port conflict from stale process

System behavior:

- mark workspace `failed`
- store failure reason + stage
- allow retry from last safe checkpoint

## 15) Detailed Implementation Plan (Non-Frontier Agent Execution Guide)

This section is intentionally explicit so a non-frontier coding agent can execute without ambiguity.

### 15.1 Execution Rules for the Agent

1. Implement phases in order. Do not skip ahead.
2. For each phase:
   - complete code changes,
   - run listed validations,
   - write/update tests,
   - only then proceed.
3. Keep each phase in a separate PR when possible.
4. Do not introduce shared default credentials.
5. Do not log secrets.

### 15.2 Phase 1: Data Model + API Contract

**Objective**: Add scaffolder-side workspace entity and API contracts for provisioning.

**Agent Tasks**:

1. Add `WorkspaceProvisionRequest` and `WorkspaceInstance` types in backend domain models.
2. Add persistence schema/migrations for workspace instances.
3. Implement API endpoints:
   - `POST /api/workspaces`
   - `GET /api/workspaces/:id`
   - `POST /api/workspaces/:id/retry-bootstrap`
4. Add request validation rules:
   - `domain` required
   - `workspaceName` required
   - reject invalid domain format
5. Add status enum lifecycle values:
   - `queued`, `infra_provisioning`, `infra_ready`, `bootstrap_running`, `health_checking`, `ready`, `failed`

**Acceptance Checks**:

1. Unit tests for request validation (valid/invalid domain).
2. Unit tests for lifecycle transitions.
3. API contract tests for 201/200/4xx/5xx cases.

### 15.3 Phase 2: Infra Provisioning Adapter

**Objective**: Provision one EC2 instance per workspace request.

**Agent Tasks**:

1. Build provider adapter interface:
   - `provisionInstance(request)`
   - `getInstanceStatus(instanceId)`
   - `terminateInstance(instanceId)` (future-safe)
2. Implement AWS-backed adapter (Terraform wrapper or SDK path, whichever scaffolder already uses).
3. Attach DNS mapping for `domain` and `opencode.<domain>`.
4. Persist infra metadata to workspace record.

**Acceptance Checks**:

1. Integration test with mocked provider adapter.
2. Verify workspace transitions to `infra_ready` after successful infra step.
3. Verify failures transition to `failed` with `statusReason`.

### 15.4 Phase 3: Bootstrap Runner

**Objective**: Clone and initialize `judigot/workspace` on the new instance.

**Agent Tasks**:

1. Implement bootstrap command runner (SSH or SSM based on existing scaffolder infra).
2. Execute commands in this order:

```bash
git clone git@github.com:judigot/workspace.git ~/workspace || true
cp ~/workspace/.env.example ~/workspace/.env || true
# write env values
cd ~/workspace && ./scripts/init.sh
~/workspace/scripts/deploy-nginx.sh
```

3. Write `.env` values before running init:
   - `DOMAIN`
   - `OPENCODE_SERVER_USERNAME`
   - `OPENCODE_SERVER_PASSWORD`
   - optional `ANTHROPIC_API_KEY`
4. If creds absent in request, generate secure random values.
5. Store generated creds in secret storage and only references in DB.

**Acceptance Checks**:

1. Bootstrap logs captured and redacted.
2. Bootstrap is re-runnable (idempotent) using retry endpoint.
3. Workspace transitions to `health_checking` after bootstrap command success.

### 15.5 Phase 4: Health Checks + Ready State

**Objective**: Validate workspace is actually usable before marking ready.

**Agent Tasks**:

1. Implement health checks with retry/backoff (e.g. 10 attempts, exponential backoff):
   - `GET https://<domain>` expects 200
   - `GET https://opencode.<domain>` expects 401 unauthenticated
   - authenticated request to `opencode` expects 200
2. Mark workspace `ready` only after all checks pass.
3. On repeated failure, mark `failed` with granular reason.

**Acceptance Checks**:

1. Unit tests for health check success/failure branching.
2. Integration test with mocked responses for 200/401/500.

### 15.6 Phase 5: UI Flow in Scaffolder

**Objective**: Expose end-to-end provisioning UX to users.

**Agent Tasks**:

1. Add "Create Workspace" form with required `domain` field.

**Acceptance Checks**:

1. UI tests for required domain validation.
2. UI tests for status progress rendering.
3. Ensure secrets are not shown in logs/network console beyond intended reveal.

### 15.7 Phase 6: Security and Guardrails

**Objective**: Ensure safe defaults and prevent insecure deployment.

**Agent Tasks**:

**Acceptance Checks**:

## 16) Acceptance Criteria

1. New workspace can be provisioned from Scaffolder with only `workspaceName` + `domain`.
2. Instance ends in `ready` with:
   - `https://<domain>` returning 200
   - `https://opencode.<domain>` returning 401 unauthenticated
3. Authenticated OpenCode access succeeds.
4. User A cannot access user B workspace resources (different instance boundary).
5. Re-running bootstrap does not break the instance.
6. Generated credentials are unique per workspace.

## 17) Risks and Mitigations

| Risk                                                             | Impact | Mitigation                                                                    |
| ---------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------- |
| Static default credentials accidentally reused                   | High   | Generate per-instance credentials by default; disallow empty password in prod |
| DNS/cert delay causes bootstrap failures                         | Medium | Retry with backoff; mark step-specific failure                                |
| Cost growth from per-user instances                              | Medium | Auto-stop policies, idle shutdown, cost dashboard                             |
| Drift between `workspace` repo changes and bootstrap assumptions | Medium | Pin bootstrap revision/tag, add compatibility check                           |
| Secret leakage in logs                                           | High   | Redact env/secrets, avoid echoing credentials                                 |
