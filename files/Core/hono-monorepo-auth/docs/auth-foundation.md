# Hono monorepo authentication foundation

Recipe: `Projects/hono-react-monorepo`. Use it with `judigot/template-monorepo`.
It layers authentication into the existing Hono API without replacing Vite,
Next.js, shared packages, CI, Docker, or the runtime/Vercel adapters.

This is deliberately an auth-only recipe, not a generic domain CRUD generator.
The input must contain UUID `user.id` and UUID `session.userId` referencing it.
Better Auth owns the complete user/session/account/verification schema; legacy
`hashed_password` is not copied onto user records. Passwords live in the
credential account table. Extra domain tables are not generated by this recipe.
Do not use this recipe as a migration of an existing populated auth database.

Configure `DATABASE_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET` (random,
at least 32 characters) and exact `CORS_ORIGINS`. Production requires HTTPS.
Run `bun run --cwd apps/api db:migrate` before serving authentication requests.
Never run migrations automatically on server startup or serverless requests.

Routes: `/api/auth/*` is handled by Better Auth, and `/api/me` requires a valid
session and returns only public user fields. There are no user/session CRUD
routes. Email/password signup requires a 12-character password. Email delivery,
verification enforcement, password reset delivery, roles and tenant permissions
must be configured for the product's requirements before public launch.

Use same-origin proxies for frontend authentication where possible. Direct
cross-origin browser requests must include credentials; allow only explicitly
configured frontend origins. Cross-site cookies and platform ingress rate limits
require a deliberate deployment configuration. Auth rate limits persist in the
database across instances. Restrict direct origin access and configure a trusted
ingress that overwrites client IP headers; never trust caller-supplied forwarded
headers from the public Internet. Platform ingress abuse controls are still needed.

Run `bun run check` and `bun run test:e2e` on fresh output without formatting or
editing generated files. API tests use embedded PostgreSQL (PGlite), apply shipped
migrations, and exercise real Better Auth requests; they do not require secrets
or an external database. Also smoke-test a real PostgreSQL deployment and the
chosen hosting target before claiming production readiness.
